This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Backend for a physical cocktail-mixing machine ("CocktailMachine V2" / coma2), running on a Raspberry Pi. It's a small FastAPI + SQLAlchemy REST API backed by SQLite. Clients define drink recipes (cocktails), ingredients, and dispenser "slots" (the machine's physical ports, each loaded with one ingredient), and the API is used to check which cocktails can currently be made given what's loaded in the slots.

The stack was rewritten from an earlier Flask version on `refactor-codebase` — see `docs/refactor-requirements.md` for the scope/decisions behind that, and "Working conventions on this branch" below for how to keep working on it.

## Running the backend

Without Docker:

```bash
uv sync
uv run alembic upgrade head
uv run python -m coma2.seed   # optional: sample ingredients/cocktails/slots
uv run uvicorn coma2.main:app --host 0.0.0.0 --port 5055
```

Interactive API docs (auto-generated by FastAPI) are served at `/docs` (Swagger UI) and `/redoc`.

With Docker: `docker compose up` (builds from `Dockerfile`, maps port 5055, persists `/data` as a named volume — the sqlite db lives at `/data/coma2.db` in the container). Note the space, not a hyphen: this machine only has the Docker Compose v2 CLI plugin, not the standalone `docker-compose` v1 binary. The container's `CMD` runs `alembic upgrade head`, then `coma2.seed`, then starts uvicorn; the seed step is idempotent (checks whether tables are already populated) so restarting the container never duplicates data.

Lint/format/type-check/test: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy coma2 tests`, `uv run pytest`. All four run in CI (`.github/workflows/ci.yml`) along with a plain `docker build .`.

## Database

SQLite. DB URL comes from `coma2.config.settings.database_url` (a `pydantic-settings` `Settings` object, default `sqlite:///coma2.db`, overridable via `DATABASE_URL` env var or `.env`). In the Docker image it's pinned to `/data/coma2.db` so it persists on the mounted volume. Schema is managed by Alembic (`alembic/`, config in `alembic.ini`, one migration per table added chronologically in `alembic/versions/`) — `uv run alembic upgrade head` applies migrations; `uv run alembic revision --autogenerate -m "..."` generates a new one from model changes. `alembic/env.py` explicitly imports every feature module's `models.py` so autogenerate can see all tables — add new modules there too.

`coma2/seed.py` inserts sample data (3 ingredients, 2 cocktails, 16 empty slots) — it checks the ingredient and slot tables independently before inserting, so it's safe to run on every startup rather than a one-shot dev script.

Core tables (see `README.md` for column-level detail):
- `cocktail` — id, timestamp, name
- `ingredient` — id, timestamp, name, alcohol_percentage
- `cocktail_ingredient` — many-to-many join table between cocktail and ingredient, with an `amount` column (composite PK of both foreign keys)
- `slot` — id, ingredient_id, amount_percentage — represents a physical dispenser slot on the machine and which ingredient (if any) is currently loaded into it. `ingredient_id = 0` means the slot is empty/unassigned (plain integer, not a real FK — there is no ingredient with id 0).

## Architecture

`coma2/main.py` is the FastAPI app instance and composition root — it includes each feature module's router and holds only the cross-cutting `/api/health` route. `coma2/config.py` holds the `pydantic-settings` `Settings` object. `coma2/database.py` holds the SQLAlchemy 2.0 engine, `SessionLocal`, `Base`, and the `get_db` FastAPI dependency (injected into routes via `Depends`).

Feature modules live one-per-folder under `coma2/<feature>/`:
```
coma2/<feature>/
  router.py   # FastAPI APIRouter, one route function per operation
  models.py   # SQLAlchemy 2.0 ORM model(s), using Mapped[]/mapped_column()
  schemas.py  # Pydantic request/response models
```
- `coma2/ingredients/` — full CRUD (`POST`/`GET`/`GET {id}`/`PUT {id}`/`DELETE {id}`) with a DB-level unique constraint on name. Deleting an ingredient cascades: any cocktail requiring it is deleted (via `Cocktail`'s `cascade="all, delete-orphan"` on its `CocktailIngredient` rows), and any slot loaded with it is cleared (`ingredient_id -> 0`) — see the docstring on `delete_ingredient` in `coma2/ingredients/router.py`. This is the one place ingredients reaches into cocktails' and slots' models.
- `coma2/cocktails/` — full CRUD; `PUT` replaces the ingredients list wholesale rather than diffing it. `GET /api/cocktails/available` intersects each cocktail's required ingredient ids against everything currently loaded across all slots (excluding empty slots) using a set-subset check. **Route ordering matters**: `/available` is registered before `/{cocktail_id}` in `router.py` because FastAPI/Starlette matches routes in registration order (unlike Flask/Werkzeug, which prefers static segments automatically) — a dynamic route registered first would shadow it.
- `coma2/slots/` — `GET` (list) and `PATCH {id}` only; there's no create endpoint because slots represent a fixed set of physical ports established once via the seed script, not a resource clients create.

Validation lives in Pydantic schemas (e.g. `alcohol_percentage`/`amount_percentage` constrained 0–100, cocktail ingredient lists require at least one entry with a positive amount) rather than manual `if` checks in routes. API docs are auto-generated by FastAPI from routes + schemas, served at `/docs` (Swagger UI, supports executing requests directly against a running instance) and `/redoc` — there is no hand-maintained OpenAPI file and no Postman collection; manual testing happens through `/docs`.

## Testing

`tests/conftest.py` provides two function-scoped fixtures used by every test: `db_session` (a fresh in-memory SQLite DB per test, via `StaticPool` so the single connection persists for the test's duration) and `client` (a `TestClient` with `get_db` overridden to use that same session). New feature modules should import their `models` module at the top of `conftest.py` (alongside the existing imports) so `Base.metadata.create_all()` picks up their tables.

## Working conventions on this branch

- Commit in small, logical units (one coherent change per commit), using Conventional Commits messages (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`).
- Commit locally as you go; do not push until asked.
- Pause for review at each major checkpoint (e.g. after scaffolding, after each module) rather than running through the whole plan unattended.
